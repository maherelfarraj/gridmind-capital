Two related defects on `/admin/users`, found in sequence. The second was reported during review of the first.

## Round 1 — the internal invite offered roles the server always rejects

Two independent allowlists exist, and the modal used the wrong one:

- **`assignableRolesFor()`** answers *authority* — who outranks whom. Spans all 12 roles, correctly.
- **`provisionInternalUser`** enforces *identity*, and rejects `subcontractor` / `client_viewer` outright.

The invite form offered the authority list, so 2 of 12 options **could only ever error**. External identities also need an organisation for `profiles.external_org`, which that form never collected.

The **Change Role** modal had the identical defect: `updateUserRole` never passes an `externalOrg`, so `resolveExternalOrg` rejected both external roles 100% of the time. Fixing only the reported screen would have left an identical guaranteed-failure path one modal away.

`internalAssignableRolesFor()` narrows both dropdowns. `DB_EXTERNAL_ROLES` is listed **explicitly, never derived by exclusion** — derivation is fail-open, so a new external role added later and forgotten would silently classify as internal and reappear here, recreating this exact bug. A drift test pins the list to the server's `EXTERNAL_ROLES`.

## Round 2 — the external invite reported success without persisting

Testing the new hand-off, inviting `maher@tek.jo` as a subcontractor showed a success toast, then saved `role=viewer`, `user_type=internal`, `external_org=NULL`.

### Production evidence

| Fact | Value |
|---|---|
| `provision_external` audit rows, all time | **0** |
| Auth user created | **2026-07-28**, six days before the test |
| Only mutation on the account | `change_role` → `viewer` at 18:21:31Z |
| Profiles with `user_type='external'` | **0** |

Zero `provision_external` rows have **ever** been written. The external provisioning service was never reached — not by this test, not by anyone.

### Cause 1 — no conflict guard (the more serious of the two)

The email already belonged to an internal profile in the tenant, so the action took its existing-user branch. The canonical service would then have **converted a colleague's account into a subcontractor**: same tenant, assignable role, so every authority check passes. That is a privilege change disguised as an invite, reported to the admin as success.

The guard now refuses this before anything is written. **Silent conversion is the worse failure**, so this is treated as a conflict to be refused rather than an operation to be permitted.

### Cause 2 — success was never verified

The action returned success whenever no error was returned, so a partial or absent write was indistinguishable from a correct one. It now reads the row back and asserts `role`, `user_type`, `external_org` and `tenant_id` before the UI may claim the invite worked.

### Also: list separation

`getUsers` listed external identities under **Internal users**, presenting a subcontractor as a colleague and offering internal-only actions on them.

Filtered on **role OR `user_type`**, matching the canonical containment predicate (`is_external_role()`, which keys off role). Production holds a profile that is external by role and internal by column — filtering on `user_type` alone would have left it visible.

## Scope

**No migrations, no schema change, no writes to production data.** All investigation was read-only. No change to role definitions, RLS, or the provisioning service itself — the services were already correct, which is why the database showed nothing.
