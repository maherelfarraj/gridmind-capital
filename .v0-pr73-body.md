The **Invite User** modal on `/admin/users` listed **Subcontractor** and **Client Viewer**, but that form posts to `provisionInternalUser`, which rejects them outright:

```
"subcontractor" is not a valid internal role.
```

Both options were guaranteed to fail. This wasn't a validation gap on the server — the server was right and the UI was offering something it must refuse.

## Root cause

Two limits govern the invite dropdown, and only one was applied:

| Limit | Question | Was it applied? |
|---|---|---|
| **Authority** | may this admin grant that role? | yes, via `assignableRolesFor` |
| **Identity** | can this *path* create that role? | **no** |

`assignableRolesFor` deliberately spans every canonical role — correct for "who outranks whom", wrong for a form wired to the internal provisioning path. External identities also require an organisation for `profiles.external_org`, which this form has no field for.

## Fix

New `internalAssignableRolesFor` / `internalAssignableRoleOptionsFor` in `lib/auth/roles.ts` apply both limits. Applied to the invite dropdown **and** the Change Role dropdown.

`DB_EXTERNAL_ROLES` is listed explicitly rather than derived by exclusion. Derivation is fail-open here: a new external role added to `DB_USER_ROLES` and forgotten would silently classify as internal and reappear in the dropdown — exactly the defect being fixed.

## A second instance of the same bug

**Change Role** (shipped in #71) had the identical defect. It offers a role list, but `updateUserRole` never passes an `externalOrg`, so `resolveExternalOrg` rejected both external options every time. Fixing only the reported invite modal would have left a working reproduction one menu away.

## The server is still the boundary

`lib/auth/provisioning.ts` is `import 'server-only'`, so a client component cannot read the canonical `USER_TYPE_BY_ROLE`. This is a presentation-layer mirror, not a second source of truth — a test asserts it equals the canonical `EXTERNAL_ROLES` exactly, so drift fails CI rather than silently reopening the bug.

## Also

- **"Invite External User"** action in the modal footer switches to the External access tab, so the removed roles lead somewhere instead of vanishing.
- **Full name** field added to the external form. It was collected for internal invites but not external ones, so every external user was created with a blank `full_name`. Display metadata only, never authority.
