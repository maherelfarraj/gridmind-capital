## Summary

Three related defects in user provisioning, plus an audited repair path for the production data one of them damaged.

Reported symptom: inviting an external user saved them as `role=viewer, user_type=internal, external_org=NULL` and listed them under **Internal users**. Investigating that surfaced two further problems, one of which silently converted a real internal colleague into a subcontractor.

**No migrations.** One production data repair, described below.

---

## Round 1 — the internal invite offered roles the server always rejects

Two independent allowlists existed and the modal used the wrong one:

- `assignableRolesFor()` answers **authority** — who outranks whom. Spans all 12 roles, correctly.
- `provisionInternalUser` enforces **identity** — and rejects `subcontractor` / `client_viewer` outright.

The invite modal used the authority list, so 2 of its 12 options could only ever produce an error. External identities also require an organisation for `profiles.external_org`, which that form never collected.

`internalAssignableRolesFor()` now narrows the list. `DB_EXTERNAL_ROLES` is enumerated **explicitly rather than derived by exclusion** — derivation is fail-open, so a new external role added later and forgotten would silently classify as internal and reappear here. A drift test pins the list to the server's `EXTERNAL_ROLES`.

The same defect existed in the Change Role modal (`updateUserRole` never passes `externalOrg`, so `resolveExternalOrg` rejects both external roles 100% of the time). Both are narrowed.

---

## Round 2 — the external invite never verified what it wrote

**The decisive evidence was an absence:** `SELECT count(*) FROM audit_log WHERE new_values->>'op'='provision_external'` returned **0, ever**. `provisionExternalUser` always writes that row, so the canonical service had never run. The failure was upstream, in the action.

Two causes:

1. **No conflict guard.** `auth.users.created_at` for the invited address was 5 days before the invite, so the flow took its existing-user branch. The service would then have rewritten an internal account into a subcontractor — same tenant, assignable role, so every authorization check passes.
2. **Success was never verified.** The action returned success whenever no error came back, without re-reading the row. A partial or absent write was indistinguishable from a correct one. That is precisely why the UI reported "Access updated" over wrong database state.

Also: `getUsers` listed external identities under Internal users. It now filters on **role OR user_type**. Production holds a profile that is external by role and internal by column; filtering on `user_type` alone would still have leaked it.

---

## Round 3 — a guard in the action shell is not a guard

Browser verification of round 2 **converted a real internal user anyway** and toasted success.

The deployed preview was confirmed to be running the round-2 commit, with the guard present in the remote blob. It still converted `engineer/internal` → `subcontractor/external`.

**The guard lived only in `inviteExternalUser`.** `provisionExternalUser` — the single writer every caller must traverse — still permitted the conversion by design. A guard in one action shell protects one entry point.

The refusal now lives in the writer. The action keeps the friendly message.

`adoptNewlyInvited` remains exempt, and is the only legitimate internal→external conversion: `handle_new_user` writes a fail-closed internal shell (`viewer`/`internal`) for every fresh invite, so a genuine new external invite always passes through internal shape. That flag is provenance, not preference — it is the same signal that authorizes compensation to delete the auth user, so it cannot be true for a user merely looked up.

**The testing lesson:** five green tests on `externalInviteConflict()` proved a helper returns the right string. They could not prove the feature worked. Seven tests now drive the real `inviteExternalUser` entry point and assert the negatives — no write, no auth invite, no provisioning call.

---

## Repair path

`revertUnintendedExternalConversion` — admin-gated, audited, reversible.

Restored values are read out of the conversion's **own audit row**, never supplied by the caller, so this cannot set an arbitrary role. If the audit trail does not prove what the account was, or the account has changed since, the reversal is refused rather than guessed.

Scope is deliberately narrow: `role`, `user_type`, `external_org`, and revoking external grants. `tenant_id` and `is_active` are never written — the conversion did not change them, and a repair that touches more than it broke is not a repair.

Split into a pure planner and an executor, matching the existing `lib/admin` pattern (vitest env is `node`, no DOM harness). The server action and the operator script call the same service, so no second code path can drift.

### Production repair applied

`ahmad+gcm@gsi.jo` ("Grid Connection Manager (pilot)") restored:

| | Before repair | After repair |
|---|---|---|
| role | `subcontractor` | `engineer` |
| user_type | `external` | `internal` |
| external_org | `Test Vendor Company` | `NULL` |
| tenant_id / is_active | unchanged | unchanged |

Dry run first, output matched the target exactly, then applied. 0 grants revoked (there were none, so no data was ever exposed). Verified independently: appears only under Internal users; subcontractors back to 1; active external users back to 1.

`maher@tek.jo` was left external — it is a genuine test account, not a converted colleague.

## Verification

- **326/326 tests** (291 baseline + 35 new), typecheck clean, build clean
- **14 mutations** across the three guard sets, each caught by distinct tests, baselines restored byte-identical
- Mutation M1 is the load-bearing one: narrowing identity classification to `user_type` alone still leaks the legacy production row

## Not verified

Browser testing of the invite flows requires an authenticated admin session. When testing the external invite, note that inviting an **existing internal** address is now expected to produce an explicit error, not success — converting a colleague should be a deliberate act, not a side effect of an invite.

## Worth a product decision

`ahmad+gcm@gsi.jo` suggests internal→external conversion may be a real business need. If so it belongs in an explicit "convert user" flow with its own confirmation, not as a side effect of an invite.
