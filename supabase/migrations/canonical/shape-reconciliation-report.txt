WHY 128 WAS WRONG
  128 corresponds to no rule that was actually run: it is neither the
  public-to-public subset (145) nor the total (153). It is a stale figure that
  was carried forward and then blessed with "all match" -- and that is the real
  defect. A count compared against an unstated rule cannot be verified by anyone
  reading the report, and "all match" gave it false authority. The FK dimension
  had in fact never been compared by VALUE at all, only by this number.

CANONICAL FK COUNTING RULE (now used on both sides, without exception)
  * source relation in schema public
  * pg_constraint.contype = 'f' only
  * target may be in ANY schema -- the 8 auth.users references are real foreign
    keys and excluding them is precisely the kind of silent filter that produced
    this error
  * extension-owned and platform schemas are never sources (none exist in public)
  * partition children: none today (R6 = 0), so no de-duplication is applied. If
    partitioning is introduced, inherited copies must be excluded via
    conparentid = 0 and this rule updated deliberately, not silently.
  * NOT VALID constraints are counted and flagged by the validated field

NORMALIZED FK FINGERPRINT (replaces counting as the primary check)
  Formula -- md5 over lines joined by newline, sorted by line:
    conname|src_table|src_cols|tgt_schema.tgt_table|tgt_cols|
    confmatchtype|confupdtype|confdeltype|condeferrable|condeferred|convalidated
  src_cols / tgt_cols are attribute names in KEY ORDER (conkey / confkey
  ordinality), never alphabetical: column order is semantic in a composite FK.

    PRODUCTION FK FINGERPRINT   f061c43fcdf08eccae779b7bcabe6ac6
    ON DELETE breakdown         a=37 (NO ACTION), c=106 (CASCADE), n=10 (SET NULL)

  Asserted by postcondition P-FK1. A count can no longer pass while a target,
  column order or ON DELETE action has drifted.

  D7 NOTE (2026-08-01) -- P-FK1 WAS NOT EXECUTABLE WHEN THIS SECTION WAS WRITTEN.
  confmatchtype, confupdtype and confdeltype are pg_catalog's internal "char"

  Formula -- md5 over lines joined by newline, sorted by line:
    schema.table|attnum|attname|format_type|base_typname|atttypmod|attndims|

CORRECTIONS THIS CAPTURE FORCES ON THIS REPORT

  1. This report claimed "2 exceptions" among the 28 function EXECUTE ACLs and
     named only one. THAT WAS A MISCOUNT. There is exactly ONE exception
     (increment_copilot_usage). 27 + 1 = 28, and the arithmetic closes. No
     unaccounted function ACL ever existed. The phantom gap was generated by my
     own report and then propagated into the migration as a BLOCKED banner.

  2. The report treated the absence of service_role grants as an open question.
     It is not: service_role holds the full 8-privilege set on ALL 103 tables,
     ALL 6 views, and SELECT/UPDATE/USAGE on both sequences. The prior pass
     deleted this grant because it was unverified. That was the correct method
     -- and it produced the wrong artifact. Both halves of that sentence matter:
     the deletion prevented an invented ACL from shipping, and it also left a
     baseline that would reject the service-role key on every table.

  3. The schema-USAGE gap was real but ALREADY SATISFIED in production, with a
     property the original note missed: grantor is pg_database_owner. A baseline
     executed as postgres cannot reproduce that grantor. Semantic reproduction
     is achievable; byte-identical reproduction is not.

  4. Column ACLs: production has ZERO non-null attacl rows. The earlier
     9720-row arithmetic reached the right conclusion by inference; attacl now
     proves it structurally. Emitting per-column grants would have created
     narrower ACLs than production has.

METHODOLOGICAL NOTE -- EFFECTIVE vs EXPLICIT PRIVILEGE
  Every privilege check in the postconditions before this pass used
  has_table_privilege() and friends, which report EFFECTIVE privilege. Those
  checks are structurally incapable of detecting the defects corrected here: a
  missing service_role grant is invisible to them, and a spurious per-column
  grant still reports "privilege present". Section 15 of the postconditions now
  reads the stored ACL arrays via aclexplode(). Effective-privilege checks
  answer "can this role do it?"; only stored ACLs answer "is the grant recorded
  the way production records it?" -- which is the question a baseline must ask.
